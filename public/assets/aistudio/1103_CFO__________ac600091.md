## 一、 核心业务痛点、底层机制与系统现状交接（录音全量还原）

### 1.1 凭证唯一性规则冲突与 FAST 批导底层缺陷
1. **三维唯一 vs 一维唯一冲突**：
   - **SAP 规则**：凭证唯一性由 `BUKRS`（公司代码）+ `GJAHR`（会计年度/期间）+ `BELNR`（凭证号）三个维度共同决定，因此跨年或跨期（如 2025 年 1 月与 2026 年 2 月）可能出现相同的凭证号。
   - **FAST 规则**：越南 FAST 仅靠单字段 `so_ct`（凭证号）做一维唯一性控制，两者存在天然规则冲突。
2. **FAST 网页端 20,000 行上限与底层存储过程 Bug**：
   - **无后台写入 API**：FAST 是越南本地小型财务软件，无后台直接写入接口且仅限内网访问，只能通过前端 Web 界面（`General Voucher`）上传 Excel 导入。
   - **20,000 行崩溃阈值**：单次导入约 20,000 条记录可正常接收，超过 20,000 条后台会报错崩溃，因此程序必须严格按 20,000 行且不截断同一张凭证的规则切分文件。
   - **数据库原子性控制缺陷**：FAST 批量导入的底层存储过程（已加密无法反编译查看）原子性控制较弱，偶发唯一性检测失效，导致同一批数据被重复写入两遍——业务端看似导入成功，但后续做报表统计与试算平衡时数据会翻倍出错。
3. **防重解决方案（在线 `update_so_ct.py` 预检 + 离线期间自检）**：
   - **在线模式**：每次生成导出文件前，必须先跑一遍 `update_voucher_no`（查询 `c11＄000000` 表中的 `so_ct` 字段），若发现凭证号已存在，自动通过迭代规则追加 `_A`、`_B`、`_C` 后缀规避重复。
   - **离线模式优化建议**：在离线模式下，可先对所导出的数据期间内部扫描一遍是否存在重复凭证号，若有重复则直接在本地转换阶段做二次更新（加上附加前/后缀）。

### 1.2 月度对账同步器（`DataReconciler`）与损益表核对闭环
1. **按日增量游标（`SAPExporter`）**：
   - 若不输入同步日期，程序自动取 FAST 数据库最新记录日期（`o11＄000000`）与 SAP 最新日期比对，拉出空白时间段逐日滚动同步（跨度大时耗时较长）；若指定具体 `cpudt`（操作日期），则仅同步指定当天数据。
2. **月底损益表对账与删错补漏机制**：
   - 当月凭证导完后，在 `10.7.3.230` 的 FAST 系统中出具 **损益表（Income Statement）**，与 SAP 损益表逐行比对（两边格式一致）。
   - 若发现某科目存在差异（如前期科目映射错误或多对一改乱），财务先在 FAST 中将该问题科目的数据手工删掉（或调用删库脚本删除），随后开启 **同步对账器（`reconcile`）**，程序会自动比对两边发生额，找出所有缺失凭证并生成补充导入文件一键补齐。

### 1.3 特殊业务转换规则交接（客商兜底与外币科目重分类）
1. **往来科目客商必填与临时客商兜底（`A0001 - A0007`）**：
   - 越南准则下应付账款（如 `2202*` 映射后的 `331111`）等往来科目必须有客商信息（`LIFNR` 供应商或 `KUNNR` 客户），否则 FAST 字段校验不通过。
   - 针对 SAP 自动生成的期末**汇兑损失/汇兑收益**等天然没有客商字段的分录，在代码 `special_transform`（原第 561 - 574 行）中硬编码补充了临时客商代码（`A0001` 至 `A0007`）以通过 FAST 校验（后续也可抽入配置表维护）。
2. **本位币与外币（业务币）科目自动重分类机制**：
   - **核心差异**：SAP 科目不区分币种（同一个应收/应付科目下既有 VND 也有 USD、EUR，靠凭证币种区分）；而 FAST 科目严格按币种拆分（如应收账款下设 VND 科目 `131111` 和 USD 科目 `131112`）。
   - **反调机制**：`config/account.yaml` 中默认只能先配置成越南盾科目（尾号为 `1`）。程序通过读取 FAST 的 `dmtk` 外币科目字典表（`MSSQLSQL.QUERY_TK`）解析出字典，当识别到凭证业务币种为外币（如 USD、EUR）时，自动将科目尾号从 `1` 反调挂到 `2`（如 `131111 -> 131112`、`331111 -> 331112`）。

## 二、 前期 6 大业务疑问的现场拍板结论（以录音最终定案为准）

| 疑问编号 | 议题名称 | 谢总（副 CFO）现场拍板定案结论 | 代码落地调整 |
| :--- | :--- | :--- | :--- |
| **疑问 1** | **Excel 模板 K/L/M/N 列借贷方向与币种定义** | 1) **本位币 vs 业务币**：越南法规要求所有交易必须折算为**记账本位币（VND 越南盾，即 SAP `DMBTR`）**；若进口交易按美金结算，则美金为**业务币/原币（SAP `WRBTR`）**，需同时记录原币、汇率与本位币。<br>2) **列坐标锁定**：<br>- **G 列（第7列）**：会计科目（SAP `hkont` 映射结果）；<br>- **K 列（第11列）**：`dr_original`（**借方外币/原币**，对应 SAP **`S` 借方**）；<br>- **L 列（第12列）**：`cr_original`（**贷方外币/原币**，对应 SAP **`H` 贷方**）；<br>- **M 列（第13列）**：`dr`（**借方本位币 VND**，对应 SAP **`S` 借方**，`dmbtr * 100`）；<br>- **N 列（第14列）**：`cr`（**贷方本位币 VND**，对应 SAP **`H` 贷方**，`dmbtr * 100`）；<br>- **AQ 列（第43列）**：分录编组号（`group_id`），同组内借贷本位币及外币相加必须严格相等，仅允许“一借一贷 / 一借多贷 / 多借一贷”。 | 严格锁定：`direction == 'S'`（借方）写第 **11 列(K)** 与第 **13 列(M)**；`direction == 'H'`（贷方）写第 **12 列(L)** 与第 **14 列(N)**；第 **43 列(AQ)** 写入拆分组号。 |
| **疑问 2** | **SAP 取数 SQL 使用 `GROUP BY` 合并同科目行是否合理？** | **完全合理，必须按科目合并（为了“降维”）！**<br>- **原因**：SAP 费用类科目核算会挂大量**成本中心（Cost Center）**，特别是月底成本分摊时，同一张凭证下同一个科目、同一个功能范围（`fkber`，成本中心的上一级，区分销售/制造/管理/研发）会有几百条不同成本中心的记录。<br>- 而越南 FAST 没有成本中心维度，只有科目维度；因此在 SQL 层去掉成本中心维度、按功能范围+科目 `GROUP BY` 合并，是为了把几百条同科目记录降维合并，避免导出数据膨胀。 | 保持 `HanaSQL` 现有 `GROUP BY` 降维聚合逻辑不变（不按成本中心拆碎）。 |
| **疑问 3** | **凭证摘要取值来源（抬头 `BKTXT` 空白怎么办？）** | **维持现状，SAP 空白就留空白（无损转换）！**<br>- **原因**：现场核查 SAP 原始表发现，不仅抬头文本 `BKTXT` 是空的，连行项目文本 `SGTXT` 也全是空的（业务录单时未填）。源头空白则导出必须保持空白，绝不能人为编造填入以免误导审计。 | 保持取 `a.bktxt` 作为 `text_summary`，空白则留空。 |
| **疑问 4** | **过账日期基准（`CPUDT` vs `BLDAT`）与跨月补记** | **绝不能用 `BLDAT`，必须以不可篡改的 `CPUDT`（系统录入日期）结合 `Period`（账期）推算！**<br>- **原因**：`BLDAT` 可人为随意修改、毫无逻辑关系；而 `CPUDT` 是系统物理生成的时间戳，不可篡改，必须作为增量同步口径以保证数据连续不断档。<br>- **跨期压缩规则**：当 `CPUDT` 与账期（`Period`）矛盾时（例如 10 月 5 日补录 9 月账期的凭证），将该凭证的过账日期统一**压缩记在所属账期月份的最后一天（9月月末）**。 | 保持 `resolve_period_date(cpudt, year, period)` 逻辑不变。 |
| **疑问 5** | **为什么项目叫 `2396fast`，但 SQL 写死 `2390`？** | **确认只同步越南工厂 `2390`！**<br>- **原因**：谢总现场确认 `2396` 是美国工厂（Fusion）的代码，当时在美国出差写代码建文件夹时随手敲错了；实际越南工厂账套就是 **`2390`**，不涉及多账套扩展（注：未来高盛主体可能会复用这套方案省软件费，但当前仅同步 `2390`）。 | 保持 SQL 針對越南工厂 `2390` 取数，支持通过环境变量灵活配置。 |
| **疑问 6** | **`N009` 过渡科目与 `6051000001` 重复映射（`51181` vs `51182`）** | 1) **`N009` 过渡科目**：属于业务层面的合法多对一过渡科目（期末借贷相抵恒为 0），保留不动。<br>2) **`6051000001`（租金收入）现场拍板定案**：YAML 第 144 行配了 `'51181'`（外部），第 172 行又重复配了 `'51182'`（内部），导致解析字典时被后面的 `'51182'` 覆盖。谢总评估若要区分内部，需跨行去抓整张凭证另一方（应收账款方）的 4 位数内部客商代码再反调，太过繁琐且该科目发生额极小，当场拍板：**“没有几个数的，全部映射到外部算了！留 `51181` 就好了，把第二个（`51182`）拿掉！”** | 1) 保留 `N009` 过渡科目；<br>2) **强制锁定 `6051000001 -> 51181`（外部收入）**，移除第 172 行 `51182` 的覆盖影响，不做复杂的内部客商判断。 |

## 三、 CFO 新增开发需求规格（需求 6 & 需求 7）

### 需求 6：SAP 与 FAST 映射数据新增、修改管理 (`MappingManager`)

#### 6.1 新增客商数据、科目数据映射
- 向 `config/account.yaml` 文件中增加对应的客商或科目映射关系；
- 新增前自动校验目标新的 FAST 客商代码是否已存在于映射表中，确保不存在重复后再写入（此外可扩展：在解析凭证遇到未映射的 10 位 SAP 科目时，支持提示手动输入映射并自动写入 YAML 配置表）。

#### 6.2 修改客商数据、科目数据映射
- **6.21 修改客商数据映射**：
  1. 判断新的客商数据是否已存在，若已存在则发出提醒，否则修改 `config/account.yaml` 中对应的映射关系；
  2. 同步批量更新 FAST 数据库（`10.7.3.230`）各月历史分表中对应的客商数据；
  3. 是否保留修改日志备查：**默认保留**（写入 `logs/mapping_change_audit.log`）。
- **6.22 修改科目数据映射（含“多对一”核心风控锁）**：
  1. **一对一原则**：由于 SAP 科目细、FAST 科目粗，存在大量“多对一”（如 SAP 的 A 科目和 B 科目同时映射到 FAST 的 C 科目）。若仅修改 A 科目的映射而直接去刷 FAST 历史库中的 C 科目，会把属于 B 科目的历史凭证也错误改掉！因此**原则上禁止直接修改多对一科目，除非检测确认该映射是严格的「一对一」关系**；
  2. **多对一确认机制**：若修改的确实是多对一/多对多映射关系，必须拦截并要求人工确认（`--force-multi`）是否需要同步更新 FAST 数据库中所有相关科目数据；
  3. 确认后同步更新 FAST 数据库各月分表（`d11＄`、`r00＄`、`i11＄`、`ct00`）中的科目代码，并**默认保留修改日志备查**。

### 需求 7：实现自动登录 FAST 网页、上传导入文件、Post 到总账的自动化操作

完整串联并打通 `utils/` 下已测试通过的 Chrome CDP 协议组件：
1. 开启 Chrome 浏览器 CDP 协议及远程调试模式（默认端口 `9222`）；
2. 执行 `chrome_launcher.py` 脚本启动浏览器，通过 `login_handler.py` 导航至 FAST 内网登录网页；
3. 输入账号和密码完成登录（现场已通过浏览器 Inspect 提取 11 位密码并私发交接）；
4. 通过 `upload_handler.py`（基于 JS 控件识别）自动进入 `General Voucher` 页面，循环上传切分好的 `.result.xlsx` 导入文件（如 10 至 20 个分卷文件自动轮询上传）并归档已传文件；
5. 通过 `posting_handler.py` 自动进入总账过账页面，批量循环勾选并执行 Post 到总账（GL）操作，彻底解决财务手工过账 5 万多条记录过慢的痛点。
